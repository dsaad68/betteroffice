## Reference vs candidate

Slide 5 ("Assets Received") is a dark-navy-banded title over three side-by-side data tables listing received assets (Resource Name / Type / Status, with green/yellow status cells), an "Solutions" callout box with an partner bullet list and logo, and a dark footer bar. LibreOffice renders the full title, a white rule under it, all three tables with their grid, fills, and text, a white "Solutions" heading, and a footer reading "5 Solutions" (clipped, see finding 5). BetterOffice renders a much smaller/thinner title, no rule, three empty dashed placeholder boxes labeled "Table" in place of all table content, "Solutions" in illegible dark gray, and a footer reading the full authored text "116 Assets + 5 Solutions". The three unrendered tables cover most of the slide's area and are why `hot_cells` (r2c2, r2c3, r3c2, r3c3 — all 79–81% different) span the middle and lower-middle of the frame.

## Findings

### 1. All three tables render as empty placeholder boxes

- Where: `Table 6` (id 7, x 0.015–0.249), `Table 11` (id 12, x 0.253–0.512), `Table 12` (id 13, x 0.516–0.788), all spanning y 0.167–0.892.
- Reference: LibreOffice draws each table's grid lines, its blue/white header and banded row fills, the green/yellow status-column fills, and every cell's text (dozens of file-name rows per table).
- Candidate: BetterOffice draws a plain white box with a light dashed border and the literal word "Table" centered in it — no grid, no fills, no cell text — for all three tables.
- XML:
  ```xml
  <a:graphic><a:graphicData uri="http://schemas.openxmlformats.org/drawingml/2006/table">
    <a:tbl>
      <a:tblPr firstRow="1" firstCol="1" bandRow="1"/>
      <a:tblGrid><a:gridCol w="1999451"/><a:gridCol w="389954"/><a:gridCol w="453454"/></a:tblGrid>
      <a:tr h="142730"><a:tc><a:txBody>...</a:txBody></a:tc>...</a:tr>
      ...
    </a:tbl>
  </a:graphicData></a:graphic>
  ```
- Why the candidate is wrong: the table markup is a standard, well-formed `a:tbl` (grid, rows, cells, per-cell text) with nothing exotic; BetterOffice appears to fall back to an unimplemented-table placeholder rather than drawing the table graphic at all. This single issue accounts for the bulk of the slide's diff.

### 2. Title text rendered at roughly half the specified size

- Where: `Rectangle 10` (id 11), "Assets Received", region [0.022, 0.053, 0.979, 0.139].
- Reference: glyph ink spans rows 24–85 of the 720px-tall frame (61px), consistent with a bold 36pt heading.
- Candidate: glyph ink spans rows 51–81 (30px) at the same x-range — about half the reference's height — and visibly thinner strokes.
- XML:
  ```xml
  <a:rPr lang="en-US" sz="3600" b="1" spc="-100">
    <a:solidFill><a:srgbClr val="FFFFFF"/></a:solidFill>
    <a:latin typeface="Segoe UI"/>
    <a:ea typeface="Segoe UI Black" panose="020B0A02040204020203"/>
  </a:rPr>
  ```
- Why the candidate is wrong: the run explicitly requests 36pt bold; halving the rendered glyph height (not just a bold/weight difference) indicates the effective font size resolved by BetterOffice is well under the declared `sz="3600"`.

### 3. "Solutions" gradFill (solid white) resolves to dark gray

- Where: `Rectangle 13` (id 14), region [0.798, 0.167, 0.985, 0.241].
- Reference: text renders solid white (255,255,255) on the blue (`accent1`) box.
- Candidate: text renders dark gray; sampling the darkest stroke pixel in the text region gives (80, 80, 80), against the same blue background — nearly unreadable.
- XML:
  ```xml
  <a:rPr lang="en-US" sz="1600" b="1">
    <a:gradFill><a:gsLst>
      <a:gs pos="0"><a:srgbClr val="FFFFFF"/></a:gs>
      <a:gs pos="100000"><a:srgbClr val="FFFFFF"/></a:gs>
    </a:gsLst><a:lin ang="5400000" scaled="0"/></a:gradFill>
  </a:rPr>
  ```
- Why the candidate is wrong: both gradient stops are identical (`FFFFFF`), so the run must paint solid white regardless of angle; BetterOffice instead falls back to a flat (80,80,80) gray, the same unresolved-gradFill fallback color documented on this deck's slide 1 (`Rectangle 1`, id 2) — a run-level `gradFill` is not being evaluated.

### 4. Decorative rule above the title is missing

- Where: `Straight Connector 15` (id 16), region [0.023, 0.036, 0.253, 0.036] (zero-height line).
- Reference: a 57150 EMU (~4.5pt) solid white horizontal rule is drawn above "Assets Received".
- Candidate: no line is drawn; pixel sampling along the line's y-position (row 25–26) reads (36, 38, 93) — the plain navy title-band background — in the candidate, versus (255, 255, 255) in the reference.
- XML:
  ```xml
  <p:cxnSp><p:spPr><a:xfrm><a:off x="285275" y="248161"/><a:ext cx="2797810" cy="0"/></a:xfrm>
    <a:prstGeom prst="line"/><a:noFill/>
    <a:ln w="57150" cap="rnd" cmpd="sng" algn="ctr">
      <a:solidFill><a:srgbClr val="FFFFFF"/></a:solidFill>
      <a:prstDash val="solid"/><a:headEnd type="none"/><a:tailEnd type="none"/>
    </a:ln>
  </p:spPr></p:cxnSp>
  ```
- Why the candidate is wrong: the connector has an explicit non-`noFill` line (`solidFill` white, width 57150, `prstDash="solid"`) and is not hidden; BetterOffice draws nothing at all for it.

### 5. Footer text: candidate shows the full authored string, reference clips it (lo-suspect)

- Where: `Rectangle 1` (id 17), region [0.015, 0.908, 0.979, 0.981].
- Reference: shows only "5 Solutions", centered.
- Candidate: shows "116 Assets + 5 Solutions" in full, on one line.
- XML:
  ```xml
  <a:bodyPr anchor="ctr"><a:noAutofit/></a:bodyPr>
  <a:rPr sz="2400"><a:latin typeface="Segoe UI Semibold"/></a:rPr>
  <a:t>116 Assets + 5 Solutions</a:t>
  ```
- Why the candidate is wrong (it likely isn't): the shape holds one run with the full string "116 Assets + 5 Solutions", `noAutofit`, and a box only 501834 EMU tall (~one line at 24pt with the given insets). BetterOffice paints exactly the authored text on a single line, matching the XML. LibreOffice most plausibly substitutes for the unavailable "Segoe UI Semibold" font, widens the string enough to wrap it onto a second line, and then — with vertical anchor `ctr` and `noAutofit` in a single-line-height box — clips the first line, leaving only "5 Solutions" visible. Filed as `lo-suspect`.
