## Reference vs candidate

Slide 9 is a navy-headed outline slide: a bold "Conversation Guides Outline" title over a white rule, a left sidebar ("One Per" heading with an underline and a full-height navy divider, plus Financial Services/Retail/Government rows each with a blue icon), a center list of ten underlined hyperlink bullets, and a red comment box bleeding off the right edge with white instructional text. LibreOffice draws all of this: bold title and heading, three visible icons, the header rule and sidebar divider, medium-blue (theme) hyperlink text, and white comment text. BetterOffice matches text positions and the bullet list content closely, but renders the title/heading unbold, omits every icon and every zero-extent line shape (header rule, "One Per" underline, sidebar divider, bag-handle strokes), and turns the comment box's white text into a dull gray. The hyperlink color also differs, but the slide XML shows BetterOffice is the one matching direct formatting there.

## Findings

### 1. Icon shapes with `a:grpFill` render with no fill, making all three sidebar icons invisible

- Where: `Group 12` (id 13, money/Financial Services icon, region [0.029, 0.332, 0.074, 0.388]), `Group 29` (id 30, retail bag icon, region [0.041, 0.528, 0.071, 0.597]), `Group 17` (id 18, government building icon, region [0.034, 0.725, 0.074, 0.791]).
- Reference: LibreOffice fills every child shape (custGeom outlines, thin rectangle pillars/strips) with the group's `accent1` blue (`0072C6`), producing the three familiar line-art icons.
- Candidate: BetterOffice draws nothing at all for any of the icons — the sidebar shows only the row labels ("Financial Services", "Retail", "Government") with blank space above them.
- XML:
  ```xml
  <p:grpSp>
    <p:grpSpPr>...<a:solidFill><a:schemeClr val="accent1"/></a:solidFill></p:grpSpPr>
    <p:sp><!-- Freeform 18, id 14 -->
      <p:spPr><a:custGeom>...</a:custGeom><a:grpFill/><a:ln><a:noFill/></a:ln></p:spPr>
    </p:sp>
  </p:grpSp>
  ```
- Why the candidate is wrong: every icon child (Freeform 18/19, Freeform 22, Rectangle 23-30, Freeform 10/11) declares `<a:grpFill/>` with no other fill on the shape itself, meaning its fill must resolve to the enclosing group's `<a:solidFill>`. BetterOffice paints these as unfilled/transparent, so the icons never appear. (Same root cause reported on slide 8 of this deck.)

### 2. Zero-extent `prstGeom="line"` shapes are never drawn, whether `p:cxnSp` or `p:sp`

- Where: `Straight Connector 41` (id 42, region [0.023, 0.036, 0.253, 0.036], the white rule under the title), `Straight Connector 36` (id 37, region [0.012, 0.297, 0.075, 0.297], the underline below "One Per"), `Straight Connector 38` (id 39, region [0.108, 0.158, 0.108, 1.0], the full-height navy sidebar divider), and `Line 12`/`Line 13`/`Line 14` (id 33/34/35, region ~[0.056, 0.538, 0.056, 0.545], the retail bag's handle strokes).
- Reference: LibreOffice strokes all four kinds of shapes using their `<a:ln>` color/width — a white rule, a black "One Per" rule, a 4.5pt navy vertical divider spanning the full slide height, and the bag's black handle lines.
- Candidate: BetterOffice draws none of them; the header has no rule, "One Per" has no underline, there is no divider between the sidebar and the content area, and the retail icon's handle is missing along with its fill.
- XML:
  ```xml
  <!-- id 39, the sidebar divider -->
  <p:cxnSp><p:spPr><a:xfrm><a:off x="1313234" y="1085553"/><a:ext cx="0" cy="5772447"/></a:xfrm>
    <a:prstGeom prst="line"/>
    <a:ln w="57150"><a:solidFill><a:srgbClr val="24265D"/></a:solidFill></a:ln>
  </p:spPr></p:cxnSp>
  <!-- id 33, a retail handle stroke, a plain p:sp not a connector -->
  <p:sp><p:spPr><a:xfrm><a:off x="5808663" y="836613"/><a:ext cx="0" cy="0"/></a:xfrm>
    <a:prstGeom prst="line"/><a:grpFill/>
    <a:ln w="15875"><a:solidFill><a:srgbClr val="000000"/></a:solidFill></a:ln>
  </p:spPr></p:sp>
  ```
- Why the candidate is wrong: all four shapes have an explicit, unambiguous `<a:ln>` stroke and a degenerate (zero cx and/or cy) bounding box, which is the standard OOXML idiom for a straight line drawn along the diagonal of its own frame. The shape kind differs (`p:cxnSp` for three, plain `p:sp` for the retail handles), so the common trigger is the zero-extent "line" geometry itself, not the connector wrapper — BetterOffice appears to skip rendering any shape whose bounding box collapses to a line rather than falling back to stroking the degenerate rect's diagonal.

### 3. `b="1"` is not applied to the title or the "One Per" heading

- Where: `Rectangle 40` (id 41, "Conversation Guides Outline", region [0.022, 0.053, 0.979, 0.139]); `TextBox 35` (id 36, "One Per", region [0.011, 0.213, 0.083, 0.277]).
- Reference: LibreOffice renders both runs bold — a heavy 36pt title and a bold "One Per" heading, each visibly thicker and taller than in the candidate.
- Candidate: BetterOffice renders both in a regular (non-bold) weight; the measured glyph height for the title drops from 41px to 32px and the strokes are visibly thinner.
- XML:
  ```xml
  <a:rPr lang="en-US" sz="3600" b="1" spc="-100">
    <a:solidFill><a:schemeClr val="bg1"/></a:solidFill>
  </a:rPr><a:t>Conversation Guides Outline</a:t>
  ...
  <a:rPr lang="en-US" sz="1050" b="1">
    <a:gradFill>...</a:gradFill>
  </a:rPr><a:t>One Per</a:t>
  ```
- Why the candidate is wrong: both runs explicitly set `b="1"`; nothing in the slide, layout, or master overrides it for these direct-formatted runs, so the bold weight should be honored as written.

### 4. `a:gradFill` on run text is not resolved; falls back to the theme's default gray instead of the gradient's actual color

- Where: `Rectangle 7` (id 8, the red comment box), region [0.871, 0.083, 1.131, 0.889].
- Reference: LibreOffice renders the comment text in solid white, matching both gradient stops (`FFFFFF` at 0% and 100%).
- Candidate: BetterOffice renders the same text in dark gray (measured RGB 80,80,80 = the theme's `dk1`/`tx1` color `505050`), which is nowhere in this run's formatting — it is the theme's generic default text color, used as a fallback when the gradient isn't resolved.
- XML:
  ```xml
  <a:rPr lang="en-US" sz="2400">
    <a:gradFill><a:gsLst>
      <a:gs pos="0"><a:srgbClr val="FFFFFF"/></a:gs>
      <a:gs pos="100000"><a:srgbClr val="FFFFFF"/></a:gs>
    </a:gsLst><a:lin ang="5400000" scaled="0"/></a:gradFill>
  </a:rPr><a:t>Basically the same as slide 7 except...</a:t>
  ```
- Why the candidate is wrong: a two-stop gradient with identical white stops is visually indistinguishable from a solid white fill; BetterOffice should paint it white (or resolve the gradient generally) instead of substituting an unrelated default color. (The same fallback happens on the "One Per" run in finding 3, but there it coincidentally matches — both gradient stops there are `tx1`, which resolves to the same `505050` the fallback also produces.)

### 5. `lo-suspect`: LibreOffice overrides the hyperlink runs' direct-formatting color with the theme `hlink` color

- Where: `Rectangle 1` (id 2, the bullet list), all 10 runs ("Overview", "State & Local Government Market Opportunity", ..., "Objection handling"), region [0.179, 0.336, 1.037, 0.596].
- Reference: LibreOffice renders every hyperlink run in a medium blue, measured RGB (0, 114, 198) = `0072C6`, which is the theme's `hlink` color.
- Candidate: BetterOffice renders the same runs in a more saturated pure blue, measured RGB (0, 0, 255) = `0000FF`.
- XML:
  ```xml
  <a:rPr lang="en-US" ... u="sng">
    <a:solidFill><a:srgbClr val="0000FF"/></a:solidFill>
    <a:hlinkClick r:id="rId3"/>
  </a:rPr><a:t>Overview</a:t>
  ```
- Why LibreOffice is suspect: every one of the 10 hyperlinked runs carries an explicit direct-formatting `<a:solidFill><a:srgbClr val="0000FF"/></a:solidFill>`, which is exactly the color BetterOffice paints. LibreOffice instead substitutes the theme's `hlink` scheme color (`0072C6`) wherever `<a:hlinkClick>` is present, discarding the run's own direct formatting — the XML gives no basis for that override.

- The title's `spc="-100"` character-spacing (condensed tracking) was not separately verified beyond the bold-weight difference already reported in finding 3.
