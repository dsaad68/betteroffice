## Reference vs candidate

This is the deck's title slide: a title-only layout with a large decorative illustration bleeding off the right and bottom edges and a Microsoft logo in the lower-left. The reference (LibreOffice) shows a solid purple background, a large bold-looking white title wrapped across two lines, and the full illustration (cloud, silhouettes, three figures, buildings, city skyline). The candidate (BetterOffice) shows a flat light-gray background, the same title text rendered much smaller in dark gray on a single line, and no illustration at all — only the Microsoft logo survives. All four hot cells in the top row are saturated (100%) because the background fill alone differs across the entire slide.

## Findings

### 1. Slide layout color-map override not honored (background purple vs. gray, title text white vs. dark gray)

- Where: whole slide background; Title 1 (id 2) text color
- Reference: solid purple background (`68217A`); title text solid white.
- Candidate: solid light-gray background (`D2D2D2`); title text solid dark gray (`505050`).
- XML:
  ```
  <!-- slideMaster1.xml: default color map -->
  <p:clrMap bg1="lt1" tx1="dk1" bg2="lt2" tx2="dk2" .../>

  <!-- slideLayout4.xml: this layout overrides it -->
  <p:clrMapOvr><a:overrideClrMapping bg1="dk1" tx1="lt1" bg2="dk2" tx2="lt2" .../></p:clrMapOvr>

  <!-- slideLayout4.xml background, resolved via the layout's own map -->
  <p:bg><p:bgRef idx="1001"><a:schemeClr val="bg2"/></p:bgRef></p:bg>
  <!-- master titleStyle text color -->
  <a:solidFill><a:schemeClr val="tx1"/></a:solidFill>
  ```
- Why the candidate is wrong: the layout declares `overrideClrMapping`, so within this layout `bg2` must resolve to `dk2` (`68217A`, purple) and `tx1` to `lt1` (`FFFFFF`, white), per the theme's `clrScheme`. The candidate instead resolves both names through the master's un-overridden map (`bg2`→`lt2`=`D2D2D2`, `tx1`→`dk1`=`505050`), i.e. it never applies the layout's `p:clrMapOvr`. This single miss explains both the wrong background fill and the wrong title text color.

### 2. Title font size falls back to the master's default instead of the layout's override

- Where: Title 1 (id 2), region ≈ [0.022, 0.303, 0.831, 0.565]
- Reference: title set in one run at roughly 58pt (measured line-height ≈ 82px/line at 1280×720), wrapping the 36-character title across two lines.
- Candidate: title set at roughly 33pt (measured glyph height ≈ 44px), fitting the whole title on a single line — close to the master `titleStyle` default of 36pt, not the layout's 58.82pt.
- XML:
  ```
  <!-- slideMaster1.xml titleStyle (generic default) -->
  <a:defRPr sz="3600" b="0" .../>

  <!-- slideLayout4.xml, Title 1 placeholder's own lstStyle (should win) -->
  <a:lstStyle><a:lvl1pPr><a:defRPr sz="5882" spc="-98" baseline="0">...</a:defRPr></a:lvl1pPr></a:lstStyle>
  ```
- Why the candidate is wrong: the slide's title run carries no explicit `sz`, so it must inherit from the nearest ancestor with a matching level style — the layout placeholder's own `lstStyle` (`sz="5882"`) — before falling back further to the master `p:titleStyle`. The candidate's measured size tracks the master default instead, indicating the layout-level `lstStyle` override on this placeholder is not being applied.

### 3. Illustration picture (EMF) not drawn

- Where: Picture 4 (id 5), region [0.268, 0.198, 1.042, 1.116] (extends past the right/bottom edges by design)
- Reference: full illustration — blue cloud, gray crowd silhouettes, three foreground figures, city skyline of buildings — anchored to the lower-right, clipped by the slide edge.
- Candidate: nothing drawn in that region; only the background shows through.
- XML: `<p:blipFill><a:blip r:embed="rId3"/></p:blipFill>` referencing `ppt/media/image7.emf`.
- Why the candidate is wrong: `bo-log.json` records `"skipped_images": 1` for this slide, confirming the renderer skipped this image outright rather than drawing it incorrectly — the source is an EMF (vector metafile), a format the candidate does not currently rasterize.
