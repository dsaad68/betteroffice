## Reference vs candidate

This is a single-word section-divider slide ("Appendix") using the "Video slide" layout, which fills the whole slide with the theme's teal accent color. The reference (LibreOffice) shows the word in large white text near the top-left. The candidate (BetterOffice) shows the same word in the same position but noticeably smaller and in dark gray, which reads as low-contrast/muddy against the teal background. Both hot cells on the left (r1c1, r2c1) are the two most different regions because LibreOffice's larger glyphs extend further down and to the right than BetterOffice's; the milder r1c2/r2c2 diffs are the tail of that same wider text spilling one grid column over.

## Findings

### 1. Slide layout color-map override not honored (title text white vs. dark gray)

- Where: Title 1 (id 2) text color, region ≈ [0.022, 0.173, 0.831, 0.566]
- Reference: title text solid white.
- Candidate: title text solid dark gray (measured pixel `505050`, exactly the theme's `dk1`).
- XML:
  ```
  <!-- slideMaster1.xml: default color map -->
  <p:clrMap bg1="lt1" tx1="dk1" bg2="lt2" tx2="dk2" .../>

  <!-- slideLayout7.xml: this layout overrides it -->
  <p:clrMapOvr><a:overrideClrMapping bg1="dk1" tx1="lt1" bg2="dk2" tx2="lt2" .../></p:clrMapOvr>

  <!-- slideLayout7.xml Title 1 placeholder's own lstStyle: a 3-stop gradFill, all stops schemeClr tx1 -->
  <a:gradFill><a:gsLst>
    <a:gs pos="91241"><a:schemeClr val="tx1"/></a:gs>
    <a:gs pos="57000"><a:schemeClr val="tx1"/></a:gs>
    <a:gs pos="18000"><a:schemeClr val="tx1"/></a:gs>
  </a:gsLst><a:lin ang="5400000" scaled="0"/></a:gradFill>
  ```
- Why the candidate is wrong: the slide's own `p:clrMapOvr` is `<a:masterClrMapping/>`, but the title placeholder's fill (the `gradFill` with three `tx1` stops) is defined in the layout, not the slide. That layout also carries its own `overrideClrMapping`, which is what the placeholder's `tx1` reference was authored against — it maps `tx1`→`lt1` (`FFFFFF`, white), turning the notionally "gradient" fill into a solid white (all three stops share the same color) — a deliberate combination to get light text on this layout's colored background. The candidate instead resolves `tx1` through the master's un-overridden map (`tx1`→`dk1`=`505050`), producing dark gray text. This is the same defect already recorded for slide 1 of this deck (a different layout, same clrMapOvr-ignored root cause), so it is systemic rather than layout-specific.

### 2. Title font size falls back to the master's default instead of the layout's override

- Where: Title 1 (id 2), region ≈ [0.022, 0.173, 0.831, 0.566]
- Reference: title glyphs measure ≈95px tall (including the descenders on "p"/"p"/"x") at 1280×720, consistent with the layout's 70.58pt.
- Candidate: title glyphs measure ≈44px tall, consistent with the master `titleStyle` default of 36pt, not the layout's 70.58pt (a ≈2.1x size ratio matches the 70.58/36=1.96x size ratio expected from the two candidate font sizes).
- XML:
  ```
  <!-- slideMaster1.xml titleStyle (generic default) -->
  <a:defRPr lang="en-US" sz="3600" b="0" .../>

  <!-- slideLayout7.xml, Title 1 placeholder's own lstStyle (should win) -->
  <a:lstStyle><a:lvl1pPr><a:defRPr sz="7058" spc="-98" baseline="0">...</a:defRPr></a:lvl1pPr></a:lstStyle>
  ```
- Why the candidate is wrong: the slide's title run (`<a:r><a:rPr lang="en-US" dirty="0"/><a:t>Appendix</a:t></a:r>`) carries no explicit `sz`, so it must inherit from the nearest ancestor with a matching level style — the layout placeholder's own `lstStyle` (`sz="7058"`) — before falling back to the master `p:titleStyle`. The candidate's measured size tracks the master default instead, indicating the layout-level `lstStyle` override on this placeholder is not applied. Same defect and same title placeholder pattern as slide 1's finding 2.
