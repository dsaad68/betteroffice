## Reference vs candidate

Slide 6 is a two-column "Weekly meeting" / "Monthly run exec meeting" comparison with a small two-tone handshake icon in the top-right corner. The reference (LibreOffice) draws both header bars at the same large font, which causes the longer "Monthly run exec meeting" text to wrap and clip below its teal bar; the candidate instead shrinks that text to fit on one line while leaving the other header oversized and indented further into its bar. The candidate also drops the top-right icon entirely. Body paragraph text, box colors, and box positions otherwise match closely.

## Findings

### 1. Top-right handshake icon missing

- Where: Group 9 (id 10), children Picture 10 (id 11) and Picture 11 (id 12); region `[0.787, 0.084, 0.978, 0.132]`.
- Reference: renders a small two-segment handshake graphic (dark/tan/orange/gray blocks) at the top right of the slide.
- Candidate: nothing is drawn in that region — pure white background.
- XML:

### 2. Header placeholder font sizes diverge without any autofit XML

- Where: Text Placeholder 1 (id 2, idx 10, "Weekly meeting") region `[0.022, 0.208, 0.474, 0.306]`; Text Placeholder 3 (id 4, idx 11, "Monthly run exec meeting") region `[0.526, 0.208, 0.978, 0.306]`.
- Reference: both header runs render at the same size — measured cap-height of the first text line is 45px ("Weekly meeting") vs 44px ("Monthly run exec meeting"). Because the box is only 673454 EMU (~53pt) tall, the longer "Monthly run exec meeting " text (plus its trailing blank paragraph) wraps to a second line and is clipped by the bar below.
- Candidate: "Weekly meeting" renders at 47px cap-height (matching/slightly exceeding the reference), but "Monthly run exec meeting" renders at only 26px cap-height — about 59% as tall — letting it fit on a single line inside the same box.
- XML:
  ```
  <p:sp><!-- id=2, idx=10 --><p:spPr><a:xfrm><a:off x="269241" y="1427715"/><a:ext cx="5515274" cy="673454"/></a:xfrm>...
    <p:txBody><a:bodyPr/><a:lstStyle/><a:p><a:r><a:rPr lang="en-US" dirty="0">...<a:t>Weekly meeting</a:t></a:r></a:p></p:txBody></p:sp>
  <p:sp><!-- id=4, idx=11 --><p:spPr><a:xfrm><a:off x="6407430" y="1427715"/><a:ext cx="5515274" cy="673454"/></a:xfrm>...
    <p:txBody><a:bodyPr/><a:lstStyle/><a:p><a:r>...<a:t>Monthly run exec meeting </a:t></a:r></a:p><a:p><a:endParaRPr.../></a:p></p:txBody></p:sp>
  ```
  Layout (`slideLayout17.xml`) for both idx 10 and idx 11: `<a:bodyPr wrap="square"><a:spAutoFit/></a:bodyPr>` and `<a:lstStyle><a:lvl1pPr>...<a:defRPr sz="3529">` — identical for both placeholders, no `normAutofit`/`fontScale` anywhere in the chain.
- Why the candidate is wrong: neither the slide nor the layout gives these two runs different sizes, and `spAutoFit` means "resize the shape to fit the text," not "shrink the text to fit the shape" (that would be `normAutofit`). The reference's uniform, unscaled size is what the XML supports; the candidate appears to invent a per-shape shrink-to-fit that isn't backed by any attribute, producing two differently-sized headers that were meant to match.

### 3. Header placeholder text insets overshoot the default

- Where: same two placeholders as finding 2, region `[0.022, 0.208, 0.474, 0.306]` (pattern repeats at `[0.526, 0.208, 0.978, 0.306]`).
- Reference: "Weekly meeting" first ink pixel at x=30 (box left edge x=28), y=155 (box top y=150) — a ~2px/~5px left/top offset, consistent with the OOXML default insets (91440/45720 EMU ≈ 10px/5px at 96dpi) minus glyph side-bearing.
- Candidate: same glyph's first ink pixel at x=74, y=165 — a ~46px/~15px left/top offset, far beyond the default inset.
- XML: neither the slide `<a:bodyPr/>` nor the layout `<a:bodyPr wrap="square"><a:spAutoFit/></a:bodyPr>` specifies `lIns`/`tIns`/`anchor`, so both should fall back to the OOXML defaults (91440/45720 EMU, anchor "t"). The sibling body paragraphs on this same slide (Rectangle 5/8, which do carry explicit `lIns="182880" tIns="146304"`) line up within 2px between engines, so the renderer's basic inset handling is otherwise correct — this drift is specific to the placeholders that rely on the *default* inset.
- Why the candidate is wrong: with no inset override in scope, the candidate's text should sit at the same near-default offset the reference uses; instead it pushes text noticeably right and down.
