## Reference vs candidate

The slide is a seven-step process-flow diagram: seven `homePlate` (chevron) autoshapes in a horizontal band, each filled with a progressively lighter shade of blue (from `002060` navy to `81ABFF` pale blue) and labeled with white text, with a supporting-detail paragraph below each chevron. LibreOffice draws every chevron label in solid white, giving strong contrast against every fill shade. BetterOffice draws every chevron label in a dark gray instead, so the labels on the mid-tone fills ("Finalize Design", "Initiate Build") are nearly unreadable and the rest have visibly reduced contrast versus the reference.

## Findings

### 1. Chevron labels use the dark theme color instead of the style-referenced light color

- Where: all seven `homePlate` shapes in the process band — `Pentagon 4` (id 5, "Initiate change request") through `Pentagon 23` (id 24, "Post-launch follow up"), region `[0.007, 0.191, 0.997, 0.327]`. This is exactly the row-2 band flagged by all four "major" hot cells (r2c1 22.1%, r2c2 19.9%, r2c3 20.8%, r2c4 19.1%).
- Reference: every label ("Initiate change request", "Identify Initiative Priority", "Finalize Design", "Initiate Build", "Create & Send Comms", "Execute Launch", "Post-launch follow up") is drawn in solid white.
- Candidate: every label is drawn in a dark gray (visually matching the slide title's `dk1` color, `505050`), not white. Confirmed by cropping and zooming the chevron band in both renders: LibreOffice text is uniformly white on every fill shade; BetterOffice text is uniformly the same dark gray on every fill shade, including the lightest fill (`81ABFF`) where it still doesn't reach the reference's contrast, and the mid-tone fills (`003FBC`, `004EEA`) where the label nearly disappears into the background.
- XML (representative shape, id 19 "Identify Initiative Priority" — all seven follow the same pattern):
```xml
<p:sp>
  <p:nvSpPr><p:cNvPr id="19" name="Pentagon 18"/>...</p:nvSpPr>
  <p:spPr>
    <a:prstGeom prst="homePlate">...</a:prstGeom>
    <a:solidFill><a:srgbClr val="002B82"/></a:solidFill>
  </p:spPr>
  <p:style>
    <a:lnRef idx="2"><a:schemeClr val="accent1"><a:shade val="50000"/></a:schemeClr></a:lnRef>
    <a:fillRef idx="1"><a:schemeClr val="accent1"/></a:fillRef>
    <a:effectRef idx="0"><a:schemeClr val="accent1"/></a:effectRef>
    <a:fontRef idx="minor"><a:schemeClr val="lt1"/></a:fontRef>
  </p:style>
  <p:txBody>
    <a:p><a:r><a:rPr lang="en-US" sz="1400" dirty="0"/><a:t>Identify Initiative Priority</a:t></a:r></a:p>
  </p:txBody>
</p:sp>
```
None of the seven runs carries an explicit `<a:solidFill>` inside `<a:rPr>`, so the text color must come from the shape's own `p:style/a:fontRef`, which names `schemeClr val="lt1"`. The master's `<p:clrMap bg1="lt1" .../>` leaves `lt1` unmapped-through (maps to itself), and the theme resolves `lt1` to `FFFFFF` (white) and `dk1` to `505050` (the gray actually drawn). BetterOffice is not resolving the shape style's `fontRef` color for runs that omit an explicit run color, and falls back to the default/text color (`dk1`) instead.
- Why the candidate is wrong: per the OOXML shape style model (ECMA-376 §20.1.4.1.14, `CT_ShapeStyle`), `fontRef` supplies the default text color for the shape's text when no more specific color is set at the run, paragraph, or list-style level. Every run here is a bare `<a:rPr sz="1400" dirty="0"/>` with no fill, so `fontRef`'s `schemeClr val="lt1"` (white) should win. BetterOffice instead renders the generic/master text color, which is the `text-inheritance`/`theme-color` resolution path being skipped for shape-style-derived font color.
