## Reference vs candidate

Slide 2 is a two-column "Overview" layout: a teal header bar reading "Purpose" over a paragraph of body text on the left, and a teal header bar reading "Topics" over a three-item bullet list on the right, both sitting on light-gray content boxes. LibreOffice renders both teal headers with bold white text and renders the Topics list with bullet glyphs and a hanging indent that separates each item. BetterOffice renders the header text in the theme's dark default text color at a lighter weight, and renders the Topics list as four flush-left lines with no bullets and no hanging indent, so the three list items visually run together.

## Findings

### 1. Header labels render in the dark theme text color instead of white

- Where: Rectangle 3 "Purpose" (id 4) and Rectangle 9 "Topics" (id 10), teal header bars at roughly y 0.224–0.331.
- Reference: "Purpose" and "Topics" render in solid white, matching the two-stop white gradient on the run.
- Candidate: both labels render in the dark default text color (sampled RGB ≈ 80,80,80, matching theme `dk1` = `505050` from `theme.xml`), as if no fill was resolved for the run and it fell back to the theme default.
- XML:
```xml
<a:rPr lang="en-US" sz="2400" b="1" dirty="0">
  <a:gradFill>
    <a:gsLst>
      <a:gs pos="0"><a:srgbClr val="FFFFFF"/></a:gs>
      <a:gs pos="100000"><a:srgbClr val="FFFFFF"/></a:gs>
    </a:gsLst>
    <a:lin ang="5400000" scaled="0"/>
  </a:gradFill>
  ...
</a:rPr>
```
- Why the candidate is wrong: the run has an explicit `a:gradFill` (a degenerate two-stop white-to-white linear gradient, i.e. solid white) instead of `a:solidFill`. The candidate appears to only look for `a:solidFill` on run properties and silently drops to the inherited default color when it finds a gradient fill instead.

### 2. Header labels render at a lighter weight than requested

- Where: same two shapes and region as finding 1.
- Reference: "Purpose"/"Topics" render bold, in a rounded sans typeface (LibreOffice's fallback for the unavailable "Segoe UI Semibold").
- Candidate: both labels render in a thin/regular weight.
- XML: `<a:rPr lang="en-US" sz="2400" b="1" dirty="0"><a:latin typeface="Segoe UI Semibold" panose="020B0702040204020203" pitchFamily="34" charset="0"/>...`
- Why the candidate is wrong: `b="1"` is explicit on the run. Even with the requested typeface unavailable and a fallback family substituted, the bold attribute should still be honored on the fallback face.

### 3. Topics bullet list loses its bullet glyphs and hanging indent

- Where: Rectangle 5 "Topics" body (id 6), region roughly x 0.534–0.954, y 0.327–0.812.
- Reference: three paragraphs, each prefixed with a "•" bullet at the left edge of the text box, with wrapped continuation lines ("Contacts by Team", "Responsibilities") indented to align under the first word rather than the bullet.
- Candidate: no bullet glyph is drawn on any paragraph, and every line — first line and wrapped continuation lines alike — starts at the same left inset (the `marL` position), so the paragraph boundaries are no longer visually distinguishable from line wraps.
- XML:
```xml
<a:pPr marL="342900" indent="-342900">
  <a:buFont typeface="Arial" panose="020B0604020202020204" pitchFamily="34" charset="0"/>
  <a:buChar char="•"/>
</a:pPr>
```
- Why the candidate is wrong: each of the three list paragraphs declares an explicit `a:buChar` bullet and a hanging indent (`marL="342900"` with `indent="-342900"`, i.e. first line at 0, wrapped lines at 342900 EMU). The candidate renders neither the bullet nor the hanging indent, instead left-aligning every line at `marL`. This is a plain, non-placeholder autoshape with manually specified list formatting rather than an inherited placeholder list style, suggesting the candidate's bullet renderer is only wired up for placeholder-driven lists.

## Not reported

- Slightly different line-wrap glyph kerning inside the Purpose/Topics body paragraphs due to fallback font substitution — expected engine-to-engine font metric variance, not scored.
