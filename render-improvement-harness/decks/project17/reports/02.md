## Reference vs candidate

This is the deck's agenda slide: a dark purple header with the title "Agenda" and the Elixir logo, a gold vertical timeline with five purple circular bullets down the left, and five bordered text rows listing the agenda items. LibreOffice draws every text run in Calibri, a right-pointing white arrow inside each purple circle, and a compact header logo (infinity mark + Arabic wordmark + "ELIXIR"). BetterOffice draws visually the same layout and colors, but substitutes a wider, ligature-less fallback font for all text, replaces the circle arrows with missing-glyph boxes, and reveals an extra line of tagline text under the header logo that the reference crops off.

## Findings

### 1. Theme major font (Calibri) falls back to a wider, non-ligating face

- Where: title "Agenda" (id 2, region ≈ [0.019, 0.021, 0.101, 0.075]); all five agenda-item TextBoxes (ids 9, 24, 25, 26, 27, region ≈ [0.108, 0.202, 0.972, 0.847]); the slide-number placeholder and the master's "TOP CONFIDENTIAL" footer label.
- Reference: "Agenda" spans 88px wide (measured, x 20-108 at title font size); the first agenda line "Why we think Elixir is Uniquely positioned to serve you" spans 492px (x 100-592); "positioned" shows the connected "ti" ligature typical of Calibri/Carlito.
- Candidate: the same "Agenda" string spans 99px (+12.5%); the same agenda line spans 534px (+8.5%, x 100-634); "positioned" shows "t" and "i" as separate, unconnected glyphs with no ligature.
- XML:
  ```xml
  <!-- theme1.xml -->
  <a:majorFont><a:latin typeface="Calibri"/></a:majorFont>

  <!-- slide2.xml, TextBox 8 -->
  <a:rPr lang="en-US" sz="1600" dirty="0">
    <a:solidFill><a:srgbClr val="323232"/></a:solidFill>
    <a:latin typeface="+mj-lt"/>
  </a:rPr>
  ```
- Why the candidate is wrong: every text run on the slide resolves its Latin typeface to `+mj-lt`, which the theme fixes as `Calibri`. The candidate's measured glyph widths (roughly 8-12% wider across both a short word and a full sentence) and the absence of the "ti" ligature indicate it is not rendering with Calibri or a metrically-compatible substitute (e.g. Carlito), but with a different, wider fallback family. This is one root cause showing up on every text-bearing shape on the slide; on a more text-dense slide the extra width would risk unwanted wrapping.

### 2. Wingdings arrow glyph in the timeline bullets renders as tofu

- Where: the five purple circles down the left timeline (Oval 49-53, ids 50-54), each ≈ 0.037 wide x 0.054 tall, centered at x≈0.083.
- Reference: each circle contains a white right-pointing arrow icon.
- Candidate: each circle contains a white missing-glyph box (☐) instead of the arrow.
- XML:
  ```xml
  <a:rPr kumimoji="0" lang="en-IN" sz="1400" ...>
    <a:solidFill><a:schemeClr val="bg1"/></a:solidFill>
    <a:latin typeface="Sakkal Majalla"/>
    <a:cs typeface="Arial" charset="0"/>
    <a:sym typeface="Wingdings" panose="05000000000000000000" pitchFamily="2" charset="2"/>
  </a:rPr>
  <a:t></a:t> <!-- U+F0E8, private-use-area code point -->
  ```
- Why the candidate is wrong: the run's text is the private-use-area character U+F0E8, which only has a printable glyph under the Wingdings encoding declared via `<a:sym typeface="Wingdings" .../>`. The `<a:latin>` face (`Sakkal Majalla`) has no glyph for this code point. The candidate is evidently trying to shape the character with the Latin (or a default) font instead of falling back to the `sym` typeface, producing a notdef box on all five instances of the same run.

### 3. Header logo's source-rectangle crop is not applied

- Where: master-level "Picture 11" (id 12, slideMaster1.xml), the header logo in the top-right, region ≈ [0.907, 0.011, 0.992, 0.097].
- Reference: infinity mark, Arabic wordmark, and "ELIXIR" fill the frame cleanly with no other text visible.
- Candidate: the same three elements render slightly smaller/more compressed vertically, and a fourth line of small white tagline text appears just above the header/body boundary, immediately below "ELIXIR" — content the reference does not show at all.
- XML:
  ```xml
  <p:pic><p:nvPicPr><p:cNvPr id="12" name="Picture 11"/>...</p:nvPicPr>
  <p:blipFill rotWithShape="1">
    <a:blip r:embed="rId24" cstate="print"/>
    <a:srcRect l="15358" t="9779" r="21228" b="24405"/>
    <a:stretch/>
  </p:blipFill>
  <p:spPr><a:xfrm><a:off x="8982472" y="76200"/><a:ext cx="847328" cy="586612"/></a:xfrm>...</p:spPr></p:pic>
  ```
- Why the candidate is wrong: `a:srcRect` crops 15.4% off the left, 9.8% off the top, 21.2% off the right and 24.4% off the bottom of the source image before it is stretched into the picture frame. The reference respects this crop, so only the infinity mark and the two wordmark lines are visible. The candidate appears to stretch the full, uncropped source image into the same frame, which both reveals the cropped-away tagline row and shrinks the retained content to make room for it. Since this picture lives on the master, the same bug likely reproduces on every slide that inherits this layout.
