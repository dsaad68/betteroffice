## Reference vs candidate

The slide is a full-width data table ("Quarterly Plan | Partner Engines") with a header row (Engine, Description, a fiscal quarter Top Activities, a fiscal quarter Outcomes, a fiscal quarter Assumptions/Dependencies, Revenue Projection) and roughly a dozen data rows of dense text, occupying nearly the whole slide body below the title. The reference (LibreOffice) draws the complete table: header row filled red with white text, banded row shading, all cell text, and grid lines. The candidate (BetterOffice) draws the title correctly but shows nothing for the table area except a dashed bounding-box outline and the literal placeholder word "Table" centered inside it — no grid, no fills, no cell text.

## Findings

### 1. Table graphicFrame not rendered at all

- Where: `Table 12` (id 13), a `p:graphicFrame` at slide fraction `[0.019, 0.09, 0.975, 0.981]` — essentially the entire content area of the slide.
- Reference: Renders the full table — 6 columns × ~13 rows, red header row with white bold text, alternating row banding from the table style, borders, and all cell text content (activities, outcomes, assumptions, revenue figures for each partner engine).
- Candidate: Renders only a dashed placeholder rectangle matching the frame's bounding box, with the literal text "Table" drawn in its center — i.e. an unimplemented-element stand-in, not the table's actual content, style, or geometry.
- XML: `slide.xml` contains a well-formed table definition on this `graphicFrame`:
  ```xml
  <p:graphicFrame>
    <p:nvGraphicFramePr><p:cNvPr id="13" name="Table 12"/>...</p:nvGraphicFramePr>
    <p:xfrm><a:off x="228598" y="614247"/><a:ext cx="11663918" cy="6114288"/></p:xfrm>
    <a:graphic>
      <a:graphicData uri="http://schemas.openxmlformats.org/drawingml/2006/table">
        <a:tbl>
          <a:tblPr firstRow="1" bandRow="1">
            <a:tableStyleId>{2D5ABB26-0587-4C30-8999-92F81FD0307C}</a:tableStyleId>
          </a:tblPr>
          <a:tblGrid>
            <a:gridCol w="781495"/><a:gridCol w="2280684"/><a:gridCol w="1678254"/>
            <a:gridCol w="1235067"/><a:gridCol w="2493335"/><a:gridCol w="2181362"/>
          </a:tblGrid>
          <a:tr>...</a:tr>
          <!-- additional a:tr rows with a:tc cells and text runs -->
        </a:tbl>
      </a:graphicData>
    </a:graphic>
  </p:graphicFrame>
  ```
  This is a standard OOXML table graphic frame with `tblGrid`, a referenced table style, `firstRow`/`bandRow` banding flags, and populated rows/cells — nothing malformed or exotic about it.
- Why the candidate is wrong: The `a:tbl` graphic type inside `p:graphicFrame` is a normal, fully-specified PowerPoint table (used throughout this deck's other slides too). BetterOffice appears to fall back to an "unsupported shape" placeholder (bounding box + type name) instead of laying out and drawing the table, meaning table support for this frame is either entirely missing or failing silently (no error appears in `bo-log.json` for slide 04, `skipped_images: 0`). This is a single root cause explaining nearly the whole `fine_pct` diff and all four hot cells (r1c1, r1c2, r1c3, r4c3), since the reference has real content across the whole grid and the candidate is blank there.
