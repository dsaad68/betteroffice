## Reference vs candidate

Slide 14 is a section-divider slide: a solid dark-blue (`01178F`) background with a single "Appendix" title placeholder, left-aligned and empty otherwise. LibreOffice draws "Appendix" large (roughly 60pt) in white, filling most of the slide width. BetterOffice draws the same word much smaller and in solid black, in roughly the same top-left position.

## Findings

### 1. Title font size falls back to the master default instead of the layout's 60pt

- Where: Title 1 (id 2), region ≈ [0.022, 0.304, 0.967, 0.465]
- Reference: "Appendix" set at a large size (measured glyph bounding box ~351×81px at 1280×720, consistent with ~60pt), spanning most of the slide width.
- Candidate: "Appendix" set much smaller (measured glyph bounding box ~108×24px), roughly a 3.4x linear size difference.
- XML: the slide's `<p:sp>` for the title has an empty `<p:txBody><a:bodyPr/><a:lstStyle/>...` with no `sz` on the run, so the size must come from inheritance. The layout placeholder itself carries a size override in its own `lstStyle`, not just the master `txStyles`:
  ```xml
  <!-- slideLayout10.xml, Title 1 -->
  <a:lstStyle><a:lvl1pPr algn... sz="6000" spc="-89" baseline="0">
    <a:solidFill><a:schemeClr val="tx1"/></a:solidFill>
  </a:lvl1pPr></a:lstStyle>
  ```
  The master's `p:titleStyle` default is `sz="1962"` (~19.6pt), which is what the measured candidate size is consistent with.
- Why the candidate is wrong: per the OOXML inheritance chain (slide → slide's own placeholder `lstStyle` → layout placeholder `lstStyle` → master `txStyles`), a placeholder-shape-level `lstStyle` on the layout takes precedence over the master's `p:titleStyle`. BetterOffice appears to skip the layout placeholder's own `lstStyle` and fall straight through to the master default.

### 2. Title text color ignores the layout's color-map override

- Where: Title 1 (id 2), region ≈ [0.022, 0.304, 0.967, 0.465]
- Reference: "Appendix" rendered pure white (`RGB 255,255,255`).
- Candidate: "Appendix" rendered pure black (`RGB 0,0,0`) — not even the master's `dk1` (`505050`), i.e. plain black, no theme color at all.
- XML: the run/placeholder resolves its fill via `schemeClr val="tx1"` in the layout's `lstStyle` (see finding 1). The slide master's default color map is `tx1="dk1"`, but this layout carries its own override:
  ```xml
  <!-- slideLayout10.xml -->
  <p:clrMapOvr><a:overrideClrMapping bg1="dk1" tx1="lt1" bg2="dk2" tx2="lt2" .../></p:clrMapOvr>
  ```
  and the theme defines `lt1="FFFFFF"`, `dk1="505050"`.
- Why the candidate is wrong: for shapes on a slide whose layout declares `overrideClrMapping`, `tx1` must resolve to `lt1` (white here), not the master's `dk1`. LibreOffice's white output matches this. BetterOffice's plain black suggests it isn't resolving the scheme color through any color map at all (neither the master's nor the layout's override), and is instead falling back to a hardcoded default text color.

## Not reported

- LibreOffice's render has a 1px light-gray (`148,149,153`) border along all four image edges; this is a LibreOffice rendering artifact (no border/outline exists on the slide, layout, or master background) and not a real difference.
