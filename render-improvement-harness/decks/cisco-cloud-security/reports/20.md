## Reference vs candidate

Slide 20 is a three-card feature panel under a two-line title ("Only Cisco Cloud App Security with Elastica delivers"). LibreOffice shows the full title, three colored cards each with a bold white heading, a white circular icon (magnifying glass, network diagram, head-with-gears), and a gray caption strip below. BetterOffice shows the same layout, but the title's second line is clipped to a sliver, all three icon glyphs collapse into plain squares, the card headings render dark gray instead of white (one of them, "Intelligent Protection", is completely invisible against its matching gray fill), and the footer slide number prints as an unresolved field code.

## Findings

### 1. custGeom icon glyphs render as plain rectangles

- Where: left icon inside Group 28/Oval 29 — Freeform 30 (id 31), region ~[0.231, 0.5, 0.303, 0.63]; middle icon inside Group 33/Oval 34 — Freeform 35 (id 36), region ~[0.54, 0.505, 0.615, 0.624]; right icon inside Group 38/Oval 39/Group 40 — Freeform 41 (id 42, the head silhouette) plus the nested gear freeforms (ids 45, 46, 47, 48), region ~[0.849, 0.493, 0.927, 0.636].
- Reference: a white magnifying glass, a white network/org-chart glyph, and a white human head with two small gears, each cleanly outlined inside its circle.
- Candidate: each icon is a plain filled square (or, for the right icon, two overlapping squares) matching only the freeform's bounding box, with no trace of the authored silhouette.
- XML:
  ```
  <a:custGeom><a:avLst/><a:gdLst>
    <a:gd name="T0" fmla="*/ 858 w 1484"/><a:gd name="T1" fmla="*/ 754 h 1500"/>
    <a:gd name="T2" fmla="*/ 912 w 1484"/><a:gd name="T3" fmla="*/ 658 h 1500"/> ... (id 31)
  ```
  ```
  <a:custGeom><a:avLst/><a:gdLst><a:gd name="T0" fmla="*/ 1687 w 1710"/><a:gd name="T1" fmla="*/ 1623 h 1752"/> ... (id 42)
  ```
- Why the candidate is wrong: all three glyphs use the same `custGeom` construction — a `gdLst` of `T0..Tn` guides computed via `*/ n w W` / `*/ n h H` scale formulas, later referenced by the `path`'s `moveTo`/`lnTo`/`cubicBezTo` points. The candidate evidently fails to resolve these guide-driven points and falls back to the shape's raw bounding box, matching the pattern already seen on this deck's slide 2.

### 2. Title second line clipped instead of overflowing

- Where: Title 1 (id 2), text "Only Cisco Cloud App Security with Elastica delivers", region [0.034, 0.066, 0.96, 0.209].
- Reference: both lines ("Only Cisco Cloud App Security with Elastica" / "delivers") are fully visible, extending above and below the placeholder's nominal 0.8in-tall box since it is vertically centered with no autofit.
- Candidate: only the very top edge of the second line's ascenders ("delivers") is visible; the rest is cut off, as if the shape clips text to its bounding box.
- XML:
  ```
  master.xml Title Placeholder: <a:bodyPr vert="horz" wrap="square" ... anchor="ctr" anchorCtr="0" compatLnSpc="1">
  layout/master xfrm: <a:off x="310855" y="341313"/><a:ext cx="8469608" cy="731837"/>
  titleStyle: sz="3200", <a:lnSpc><a:spcPct val="80000"/></a:lnSpc>
  ```
- Why the candidate is wrong: the title placeholder has no `normAutofit`/`spAutoFit`, so PowerPoint/LibreOffice let two 32pt/80%-line-spacing lines overflow the shorter-than-needed 731837 EMU (~0.8in) box symmetrically around its vertical center, rather than clipping. This is the same root cause documented on slide 2 of this deck.

### 3. Card headings resolve to the wrong default text color

- Where: "SaaS Visibility" (id 28), "Extended Granular Control" (id 33), "Intelligent Protection" (id 38) — region spanning all three card tops, [0.046, 0.234, 0.959, 0.35].
- Reference: all three headings render bold white (255,255,255), giving strong contrast against the blue/gray card fills.
- Candidate: all three headings render as solid 676767 gray (measured pixel value (103,103,103), matching `dk1`/`676767` exactly). Against "Intelligent Protection"'s own `accent3` fill (also 676767) the text is 100% invisible — a pixel sample over its text region is uniformly (103,103,103)/(104,104,104) with no lighter pixels at all; against the two blue cards it is merely low-contrast.
- XML:
  ```
  <p:style><a:lnRef idx="2">...</a:lnRef><a:fillRef idx="1">...</a:fillRef><a:effectRef idx="0">...</a:effectRef>
    <a:fontRef idx="minor"><a:schemeClr val="lt1"/></a:fontRef></p:style>
  <p:txBody><a:bodyPr .../><a:p><a:r><a:rPr lang="en-US" sz="2200" b="1" dirty="0"/><a:t>SaaS Visibility </a:t></a:r></a:p></p:txBody>
  ```
- Why the candidate is wrong: none of the three runs carry a run-level `solidFill`, so the effective text color must come from the shape's style-matrix `fontRef` (`schemeClr val="lt1"` = white). The candidate instead falls back to the slide's default text color (`dk1`/676767), ignoring the `p:style` reference entirely — confirmed by the exact 676767 pixel match on all three headings.

### 4. Slide-number field shows the unresolved placeholder glyph

- Where: slide-number placeholder in the master footer, bottom-right corner, region [0.953, 0.931, 0.971, 0.944].
- Reference: renders the evaluated slide number "20".
- Candidate: renders the literal cached fallback text "‹#›".
- XML: `master.xml: <a:fld id="{4ABDCABE-3F10-B64C-92F1-862014417034}" type="slidenum"><a:rPr sz="600" .../><a:t>‹#›</a:t></a:fld>`
- Why the candidate is wrong: `type="slidenum"` fields must render as the evaluated current slide number; the candidate is echoing the cached `<a:t>` fallback text verbatim instead of substituting the real value, same as slide 2 of this deck.
