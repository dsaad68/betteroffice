## Reference vs candidate

This slide pairs a two-line title with a dashboard: a rotated green "Panel C" card over a faded duplicate card, a radar/spider chart of seven risk categories, a red "38" readiness-rating circle, a color-coded score list, and a row of four numbered green process boxes. The reference shows all of this intact — upright white card text, seven colored spokes connecting the chart's center to each category dot, a white "38", all four green boxes filled, and the full two-line title above the dashboard. The candidate mangles several independent pieces: the title's second line is sliced off mid-glyph, the green card's text is mirrored and the wrong color, the radar chart loses all seven of its spokes (only the dots remain), the fourth process box loses its green fill, and the footer's slide-number field shows raw field markup instead of "9".

## Findings

### 1. Title's second line is clipped instead of allowed to overflow

- Where: `Title 1` (id 2), text "Determine the apps that are best for your business", box inherited from the master at `[0.034, 0.066, 0.961, 0.209]` (EMU `off (310855,341313)`, `ext (8469608,731837)` against a `9144000x5143500` slide).
- Reference: renders both lines in full — a pixel scan at x=35 through the "business" glyphs shows a continuous run of dark pixels from row ~60 to ~107 (full letter height, no descenders needed), extending well past the box's own bottom edge (row ~113) with no visible cutoff.
- Candidate: line 1 renders fully, but line 2 ("business") only shows meaningful ink for rows ~105-112 — about 8 rows of the roughly 25 rows the glyphs need — then stops dead, leaving only the tops of the letters visible. Row ~112-113 lines up almost exactly with the title placeholder's bottom edge (113 px = 0.209 × 540).
- XML:
  ```
  <!-- master.xml, title placeholder bodyPr: no autofit element of any kind -->
  <a:bodyPr vert="horz" wrap="square" lIns="91424" tIns="45712" rIns="91424" bIns="45712"
            numCol="1" anchor="ctr" anchorCtr="0" compatLnSpc="1">
    <a:prstTxWarp prst="textNoShape"><a:avLst/></a:prstTxWarp>
  </a:bodyPr>
  ```
  ```
  <!-- slide9.xml, Title 1 -- no bodyPr/lstStyle overrides -->
  <p:sp><p:nvPr><p:ph type="title"/></p:nvPr>
  <p:spPr/><p:txBody><a:bodyPr/><a:lstStyle/>
    <a:p><a:r><a:rPr lang="en-US" dirty="0"/><a:t>Determine the apps that are best for your business</a:t></a:r></a:p>
  </p:txBody></p:sp>
  ```
- Why the candidate is wrong: per the OOXML default (no `normAutofit`/`spAutoFit`/`noAutofit` present anywhere in the inheritance chain), text that doesn't fit the shape is supposed to overflow visibly, not be clipped to the shape's bounding box — which is exactly what the reference does. The candidate instead hard-clips the second line right at the shape's bottom edge.

### 2. Green card's text is mirrored by the shape's rotation/flip

- Where: `Rectangle 62` (id 63, "Panel C"), region `[0.021, 0.353, 0.159, 0.775]`.
- Reference: renders "Panel C" upright, left-to-right, in the normal reading order, even though the shape itself carries `rot="10800000" flipV="1"`.
- Candidate: renders the same three words as a horizontal mirror image on each line ("ssenisuB", "ssenidaeR", "erocS"), stacked in the correct top-to-bottom order but reading right-to-left.
- XML:
  ```
  <p:sp><p:nvSpPr><p:cNvPr id="63" name="Rectangle 62"/></p:nvSpPr>
  <p:spPr>
    <a:xfrm rot="10800000" flipV="1"><a:off x="3347265" y="717630"/><a:ext cx="1261872" cy="2170239"/></a:xfrm>
    <a:prstGeom prst="rect"><a:avLst/></a:prstGeom>
    <a:solidFill><a:srgbClr val="99CC31"/></a:solidFill>
  </p:spPr>
  <p:txBody>...<a:t>Panel C</a:t>...</p:txBody></p:sp>
  ```
- Why the candidate is wrong: `rot="10800000"` (180°) combined with `flipV="1"` is the standard way to express "flip horizontally" for a shape (flip-then-rotate-180 cancels the vertical component and leaves a net horizontal mirror on the geometry/fill). Per the OOXML text model, shape flip/rotation transforms the shape's outline and fill but text runs are always laid out and drawn upright/readable — this is why the reference (and PowerPoint) never mirrors autoshape text on a flipped shape. The candidate is applying the geometry's mirror transform to the glyph layout itself.

### 3. Card and circle text use the default gray instead of the style's white font color

- Where: `Rectangle 62` (id 63, "Panel C") and `Oval 24` (id 25, "38"). Region `[0.021, 0.283, 0.67, 0.775]`.
- Reference: both render solid white text — legible white-on-green and white-on-red.
- Candidate: both render in the theme's generic gray (visually the same tone as the slide's other unstyled body text) — still legible against the green/red fills, but noticeably lower contrast and clearly not the intended color.
- XML:
  ```
  <!-- id 63 -->
  <p:style><a:fillRef idx="1"><a:schemeClr val="accent1"/></a:fillRef>
    <a:fontRef idx="minor"><a:schemeClr val="lt1"/></a:fontRef></p:style>
  <a:r><a:rPr lang="en-IN" sz="1600" b="1" dirty="0"/><a:t>Panel C</a:t></a:r>
  ```
  ```
  <!-- id 25 -->
  <p:style><a:fillRef idx="1"><a:schemeClr val="accent1"/></a:fillRef>
    <a:fontRef idx="minor"><a:schemeClr val="lt1"/></a:fontRef></p:style>
  <a:r><a:rPr lang="en-US" sz="3600" dirty="0"/><a:t>38</a:t></a:r>
  ```
- Why the candidate is wrong: neither run carries its own `solidFill`, so per the OOXML style-matrix rules the run color must resolve through the shape's `p:style/a:fontRef` (`schemeClr lt1`, theme white) — which is what the reference does. The candidate falls back to a generic default text color instead of resolving the style's font reference, the same class of bug seen on other slides in this deck.

### 4. All seven radar-chart spokes (gradient-stroked connectors) are not drawn

- Where: `Straight Connector 142` through `Straight Connector 148` (ids 143-149), the spokes of the risk radar chart inside `Group 249` (id 250). Region `[0.259, 0.278, 0.459, 0.633]`.
- Reference: draws a colored line from the chart's center to each of the seven category dots (Compliance, Data, Informational, Service, Access, Business, Administrative), each line using a two-color gradient along its length (e.g. red fading to gray, or green fading to gray) to shade the connector.
- Candidate: draws none of the seven connector lines. Only the eight small ovals (the category value dots) remain, floating with no visible connection to the chart's center or to each other — the radar/spider structure is gone.
- XML:
  ```
  <p:cxnSp><p:nvCxnSpPr><p:cNvPr id="143" name="Straight Connector 142"/></p:nvCxnSpPr>
  <p:spPr><a:xfrm flipV="1"><a:off x="3372261" y="1574644"/><a:ext cx="0" cy="830086"/></a:xfrm>
    <a:prstGeom prst="line"><a:avLst/></a:prstGeom>
    <a:ln w="19050">
      <a:gradFill>
        <a:gsLst>
          <a:gs pos="0"><a:srgbClr val="C00000"/></a:gs>
          <a:gs pos="28000"><a:srgbClr val="C00000"/></a:gs>
          <a:gs pos="30000"><a:srgbClr val="C2C2C2"/></a:gs>
          <a:gs pos="100000"><a:srgbClr val="C2C2C2"/></a:gs>
        </a:gsLst>
        <a:lin ang="5400000" scaled="1"/>
      </a:gradFill>
    </a:ln>
  </p:spPr></p:cxnSp>
  ```
- Why the candidate is wrong: every one of the seven spokes uses `<a:ln><a:gradFill>...` — a gradient fill on the line's stroke — instead of a plain `<a:ln><a:solidFill>`. This is the one property all seven connectors share and none of the deck's plain-colored lines lack, which points at gradient-filled line strokes specifically being unsupported: the renderer appears to skip drawing the stroke entirely rather than falling back to a flat color. This is the single largest contributor to the slide's diff (it hits the two highest hot cells, `r3c4` and `r3c1`) and removes an entire chart element.

### 5. Fourth process box loses its group-inherited fill

- Where: `Rounded Rectangle 100` (id 48, the "4 / Discover alternative apps to replace risky ones" box) and its numeral box `Rectangle 101` (id 50), inside `Group 99` (id 10). Region `[0.782, 0.693, 0.97, 0.866]`.
- Reference: box 4 is a solid green (`99CC31`) rounded rectangle with white text, matching the style of boxes 1-3 exactly.
- Candidate: box 4 has no fill at all — the pale gray dashboard background shows straight through it, leaving only a faint outline and hard-to-read white text; the "4" numeral area (already unfilled by design) is unaffected.
- XML:
  ```
  <!-- id 10, the group -->
  <p:grpSpPr><a:xfrm>...</a:xfrm>
    <a:solidFill><a:srgbClr val="99CC31"/></a:solidFill></p:grpSpPr>
  <!-- id 48, the box -->
  <p:spPr><a:xfrm>...</a:xfrm><a:prstGeom prst="roundRect"><a:avLst/></a:prstGeom>
    <a:grpFill/><a:ln><a:noFill/></a:ln></p:spPr>
  ```
  ```
  <!-- for comparison, id 39/42/45 (boxes 1-3) each carry their own explicit fill -->
  <a:solidFill><a:srgbClr val="99CC31"/></a:solidFill>
  ```
- Why the candidate is wrong: `<a:grpFill/>` is the standard OOXML way to say "use whatever fill is set on the enclosing group's `p:grpSpPr`" — here that's the same `99CC31` green boxes 1-3 hardcode directly. The reference resolves it correctly; the candidate treats an unresolved `a:grpFill` as no fill.

### 6. Slide-number field shows literal field markup instead of the computed number

- Where: the master's footer slide-number placeholder, bottom-right corner. Region `[0.94, 0.955, 0.98, 0.98]`.
- Reference: renders "9", the slide's actual position in the deck.
- Candidate: renders "‹#›" verbatim.
- XML:
  ```
  <!-- master.xml -->
  <a:fld id="{4ABDCABE-3F10-B64C-92F1-862014417034}" type="slidenum">
    <a:rPr lang="en-US" sz="600">...</a:rPr>
    <a:t>‹#›</a:t>
  </a:fld>
  ```
- Why the candidate is wrong: `<a:t>‹#›</a:t>` inside an `<a:fld type="slidenum">` is only the cached fallback text a reader/editor without live field support would show; a renderer with real field support is expected to substitute the shape's own position in the deck, as the reference does. This is a small, low-contrast corner element (25% alpha, 6pt), so it barely affects readability, but it is a concrete, reproducible mismatch.
