## Reference vs candidate

The slide shows a "Find problematic users automatically" title over a product mockup (blue placeholder image plus a phone/tablet screenshot) and four orange numbered callout boxes describing the feature, with an off-slide dark-red editor's note ("Please replace with new breadcrumb boxes from slide 23") bleeding in from the left edge. LibreOffice renders the editor's-note text and the four callout numbers in white, wraps the callout text across more, shorter lines, and shows the true page number "14" in the footer. BetterOffice renders the same text in a dark slate gray, wraps three of the four callouts more loosely (fewer, longer lines), and shows the raw field placeholder "‹#›" instead of "14" in the footer. The title, blue placeholder image, phone mockup screenshot, and orange box fills/positions all match closely otherwise.

## Findings

### 1. Text with no explicit run color ignores the shape's fontRef scheme color

- Where: Rectangle 73 (id 74, the off-slide red banner, region roughly x -0.105 to 0.123, y 0.362-0.762) and the four number labels "1"-"4" (Rectangle 78/86/94/101, y 0.726-0.833)
- Reference: text is white, matching the shape style's `a:fontRef` scheme color.
- Candidate: text renders as a dark slate gray on both the dark-red banner and the orange number boxes.
- XML: each affected shape carries
  ```
  <p:style>...<a:fontRef idx="minor"><a:schemeClr val="lt1"/></a:fontRef></p:style>
  <p:txBody>...<a:r><a:rPr lang="en-US" .../><a:t>...</a:t></a:r>...
  ```
  with no `a:solidFill` on the run. Compare Rounded Rectangle 76, whose body text ("Automatically analyze...") does carry an explicit `<a:solidFill><a:schemeClr val="bg1"/></a:solidFill>` on the run and renders correctly (white) in both engines.
- Why the candidate is wrong: per the OOXML shape-style mechanism, a run with no direct color inherits from the enclosing shape's `p:style/a:fontRef` (resolved through the theme/color map). BetterOffice is not applying that inheritance and instead falls back to a default text color, so every shape relying on `fontRef` alone loses its intended white text.

### 2. Numbered callout boxes wrap text differently

- Where: the three longer callout boxes, Rounded Rectangle 76 ("Automatically analyze user data assembled by Product X"), 84 ("Surface problematic users and user accounts in real-time"), 92 ("Highlight risk level of specific activities"), region x 0.197-0.773, y 0.693-0.866.
- Reference: "Automatically / analyze user / data assembled / by Product X" (4 lines); "Surface / problematic / users and user / accounts in real- / time" (5 lines); "Highlight risk / level of specific / activities" (3 lines).
- Candidate: "Automatically / analyze user data / assembled by / Product X" (3 lines); "Surface / problematic users / and user / accounts in real- / time" (5 lines, different break); "Highlight risk level / of specific / activities" (3 lines, different break) — each box fits noticeably more text per line than the reference.
- XML:
  ```
  <a:bodyPr vert="horz" lIns="457200" tIns="45720" rIns="91440" bIns="45720" rtlCol="0" anchor="ctr"/>
  ```
- Why the candidate is wrong: `lIns="457200"` reserves roughly 0.5in on the left of a ~2in-wide box — a large fraction of the available width. The consistent pattern of BetterOffice fitting more words per line than LibreOffice across all three boxes suggests the left/right insets are not being fully subtracted from the usable text width before wrapping. (Rounded Rectangle 100, "Flag suspicious behavior for investigation", shares the same `bodyPr` but its text is short enough that both engines happen to wrap it identically, so it is not listed as visibly affected.)

### 3. Footer slide-number field not evaluated

- Where: master shape "Rectangle 7" (id 12), the `sldNum` footer placeholder, bottom-right corner, region x 0.955-0.979, y 0.922-0.952.
- Reference: shows the actual page number, "14".
- Candidate: shows the literal cached field text, a "‹#›" glyph.
- XML: `<a:fld id="{4ABDCABE-3F10-B64C-92F1-862014417034}" type="slidenum">...<a:t>‹#›</a:t></a:fld>` — the `<a:t>` child of an `a:fld` is only a cached fallback value; a conformant renderer must substitute the live slide index.
- Why the candidate is wrong: the field type `slidenum` is unambiguous and the reference resolves it correctly; BetterOffice is displaying the unevaluated cached text instead of computing the slide's position in the deck.
