## Reference vs candidate

The slide contrasts "App Providers" and "Businesses" responsibilities for cloud-app security, each side a gray panel under a blue header bar, illustrated with a cluster of small vector icons (keyboard+hand, bug/hacker/skull, an open padlock over a "Cloud Apps" circle, person silhouettes with document/phone/laptop accessories, and a building). The reference (LibreOffice) draws every icon as its full illustrated glyph. The candidate (BetterOffice) gets the panels, header bars, dashed border, gray circle, title, and body text right, but every icon built from `custGeom` freeform paths is broken: about half disappear entirely, and the rest collapse into a plain colored rectangle the size of the shape's bounding box.

## Findings

### 1. Several custGeom icon groups render nothing at all

- Where: keyboard+hand icon `Group 14` (id 15, region `[0.10,0.48,0.24,0.72]`), bug icon `Group 30` (id 31, region `[0.28,0.43,0.32,0.51]`), skull icon `Group 21` (id 22, region `[0.28,0.70,0.32,0.76]`), the padlock's open shackle `Freeform 19` (id 40, region `[0.38,0.38,0.41,0.45]`), person-1 silhouette `Group 73` (id 74, region `[0.54,0.38,0.56,0.49]`), person-2 silhouette `Group 45` (id 46, region `[0.55,0.54,0.59,0.67]`), and the bug icon next to person-3 `Group 82` (id 83, region `[0.53,0.70,0.56,0.76]`).
- Reference: each draws its full icon — white keyboard+hand, red bug/skull glyphs, the blue open-shackle loop of the padlock, gray person silhouettes, a second red bug.
- Candidate: pure panel background at every one of these regions; no fill, no outline, no fragment of the shape is drawn. (Verified by pixel sampling — e.g. the keyboard region samples flat `(217,217,217)` panel gray in the candidate vs. white icon pixels in the reference.) The only surviving traces in the person-2 area are two barely-visible fragments (a couple of pixels) from the small `Rounded Rectangle`/`Rectangle` finger/phone details nested in the same group.
- XML:
  ```
  <p:grpSp><p:nvGrpSpPr><p:cNvPr id="15" name="Group 14"/></p:nvGrpSpPr>
  <p:grpSpPr><a:xfrm>...<a:chOff.../><a:chExt.../></a:xfrm>
  <a:solidFill><a:schemeClr val="bg1"/></a:solidFill></p:grpSpPr>
  <p:sp><p:cNvPr id="16" name="Freeform 5"/>...<a:custGeom>...</a:custGeom>
  <a:solidFill><a:srgbClr val="C00000"/></a:solidFill></p:sp>
  <p:sp><p:cNvPr id="17" name="Freeform 6"/>...<a:custGeom>...</a:custGeom></p:sp>
  ```
- Why the candidate is wrong: every other shape type on this slide (`round2SameRect`, `roundRect`, `oval`, plain `rect` textboxes) renders pixel-correct, so the defect is isolated to these `custGeom` shapes/groups — none of them draws even a fallback rectangle, unlike the shapes in finding 2 built the same way.

### 2. Other custGeom icons collapse to a plain bounding-box rectangle

- Where: cloud glyph `Freeform 6` (id 25, region `[0.40,0.52,0.49,0.61]`, inside the "Cloud Apps" circle group), building silhouette `Freeform 179` (id 27, region `[0.72,0.46,0.89,0.76]`), padlock body `Freeform 19` (id 41, region `[0.38,0.37,0.41,0.45]`, inside `Group 17`/id 18 — its keyhole cutout is likewise a plain rectangle instead of a keyhole shape), hacker/spy icon `Freeform 334` (id 60, region `[0.28,0.57,0.32,0.65]`, and a second instance id 62 next to person-2), the document/report icon `Group 3` (id 4, region `[0.56,0.44,0.58,0.48]`), and person-3-at-laptop `Freeform 60` (id 61, region `[0.49,0.71,0.52,0.79]`).
- Reference: cloud puff inside the gray circle, a building outline with three window bays, a rounded lock body with a keyhole notch, a fedora-and-torso hacker glyph, a folded-corner document icon, a seated person-at-laptop silhouette.
- Candidate: each is a flat, unrotated rectangle exactly spanning the shape's `a:off`/`a:ext` box, filled with the shape's own solid color (white for cloud/building, blue for the lock body, red for hacker/document icons, dark gray for the seated person) — no curve, corner, or interior cutout survives.
- XML:
  ```
  <p:sp><p:cNvPr id="27" name="Freeform 179"/>
  <a:xfrm><a:off x="8828420" y="3155110"/><a:ext cx="2027352" cy="2078675"/></a:xfrm>
  <a:custGeom><a:avLst/><a:gdLst><a:gd name="T0" fmla="*/ 597 w 631"/>...</a:gdLst>
  <a:pathLst>...</a:pathLst></a:custGeom>
  <a:solidFill><a:schemeClr val="bg1"/></a:solidFill>
  ```
- Why the candidate is wrong: `custGeom` requires evaluating the `<a:gdLst>` guide formulas (all of these shapes use the legacy `"*/ N w M"` scale-formula pattern) and drawing the resulting `<a:pathLst>` outline; painting the shape's overall extent instead discards the path entirely. This is the dominant contributor to hot cells r1c2, r2c2, r2c3, and r3c2.

### 3. Slide-number field shows garbled glyphs instead of the page number

- Where: the small slide-number placeholder in the bottom-right corner, region `[0.955,0.922,0.979,0.952]`.
- Reference: a faint light-gray "5" (25%-alpha black, 6pt).
- Candidate: several dark, bold dingbat-like symbols (not digits) at roughly the same position, clearly opaque rather than at 25% alpha.
- XML: `<a:fld type="slidenum">` carries cached text `<a:t>‹#›</a:t>` with `<a:cs typeface="CiscoSans Thin"/>` alongside `<a:latin typeface="+mn-lt"/>`.
- Why the candidate is wrong: the field should be evaluated to the actual slide number ("5") and drawn with the Latin run font at 25% black alpha; instead the candidate appears to render the cached placeholder characters through a symbol/fallback font and ignores the alpha, producing bold non-digit glyphs.

### 4. Footnote-reference digit not rendered as superscript

- Where: `TextBox 8` (id 9), region `[0.36,0.80,0.40,0.86]`, the "1" after "...security tests" in the left caption.
- Reference: a small, raised superscript "1".
- Candidate: a normal baseline-height "1", same size as the surrounding text.
- XML: `<a:rPr lang="en-US" sz="1200" baseline="30000" dirty="0">...</a:rPr><a:t>1</a:t>`.
- Why the candidate is wrong: `baseline="30000"` (30%) is an explicit superscript run property that the candidate does not apply.
