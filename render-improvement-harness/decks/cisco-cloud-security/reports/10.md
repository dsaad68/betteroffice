The reference (LibreOffice) shows the left card readable and white-on-color, all four green step boxes filled and legible, and step 3's text wrapped narrowly. ## Findings

### 1. "Panel A" / "Panel B" text renders mirrored

- Where: Rectangle 55 (id 56, "Panel A") and Rectangle 58 (id 59, "Panel B"), region ~[0.021, 0.353, 0.159, 0.775]
- Reference: both labels read normally, left to right, upright.
- Candidate: both labels render as a horizontal mirror image (backwards text), e.g. "Panel A" appears as "ϱɿoɔƧ ƚibuA".
- XML:
```xml
<a:xfrm rot="10800000" flipV="1">
  <a:off x="194361" y="1813422"/><a:ext cx="1261872" cy="2170240"/>
</a:xfrm>
```
- Why the candidate is wrong: `rot="10800000"` (180°) composed with `flipV="1"` nets to a pure horizontal reflection of the shape's geometry (harmless on a symmetric rectangle), but the candidate applies that same reflection to the text run glyphs. The reference keeps the text glyphs upright and readable, only ever mirroring the (visually symmetric) outline — text should never render as a backwards mirror image.

### 2. `grpFill` shapes render unfilled instead of inheriting the group's fill

- Where: Rounded Rectangle 100 (id 96, "Discover risky users and app locations" step box), region [0.782, 0.693, 0.97, 0.866]; and the envelope icon inside "Panel B" — Freeform 12 (id 61) plus Rectangles 13-18 (ids 62, 63, 64, 74, 75, 76), region [0.054, 0.583, 0.126, 0.663]
- Reference: step box 4 is filled the same green (`99CC31`) as steps 1-3; the icon is drawn in white on the gray card, matching its siblings.
- Candidate: step box 4 has no fill at all (the white text on it is nearly invisible); the icon is completely missing, leaving a plain gray rectangle.
- XML: both shapes use `<a:grpFill/>` and both parent groups carry an explicit color in `p:grpSpPr`:
```xml
<!-- Group 99 (parent of id 96) -->
<p:grpSpPr><a:xfrm .../><a:solidFill><a:srgbClr val="99CC31"/></a:solidFill></p:grpSpPr>
<!-- Group 59 (id 60, parent of ids 61-76) -->
<p:grpSpPr><a:xfrm .../><a:solidFill><a:schemeClr val="bg1"/></a:solidFill></p:grpSpPr>
```
- Why the candidate is wrong: `<a:grpFill/>` means "use the containing group's fill", which both parent groups explicitly set. The candidate treats `grpFill` as no-fill instead of resolving it to the ancestor group's `solidFill`.

### 3. Style-inherited text color (`fontRef`) not applied when a run has no explicit fill

- Where: Rectangle 55 (id 56), Rectangle 58 (id 59), and the step-number digits "1"-"4" (ids 86, 90, 94, 97), bounding region roughly [0.021, 0.353, 0.82, 0.833]
- Reference: all of this text renders white (255,255,255), e.g. digit "1" on its green square.
- Candidate: the same text renders dark gray (measured ~(103,103,103)) instead of white.
- XML: none of these runs set `<a:solidFill>` on their `<a:rPr>` (unlike the step-description text, which does set `<a:solidFill><a:schemeClr val="bg1"/></a:solidFill>` explicitly and renders correctly in both engines); they rely on the shape's style:
```xml
<p:style><a:fontRef idx="minor"><a:schemeClr val="lt1"/></a:fontRef></p:style>
<a:rPr lang="en-US" sz="1100" b="1" dirty="0"/><a:t>1</a:t>
```
- Why the candidate is wrong: when a run has no explicit color, its color must resolve from the shape's `p:style/a:fontRef` (here `lt1`, i.e. white). The candidate falls back to a default dark color instead of resolving through the style reference. The fact that the explicitly-colored description text renders correctly, while only the style-dependent runs are wrong, isolates the bug to `fontRef` resolution rather than white text generally.

### 4. Step 3 body text wraps at different line breaks

- Where: Rounded Rectangle 92 (id 92), region [0.585, 0.693, 0.773, 0.866]
- Reference: "Obtain a top / level statistical / view of your / organization's / risk profile" (5 lines, narrow wrap).
- Candidate: "Obtain a top level / statistical view of / your / organization's risk / profile" (different break points, one line holding only "your").
- XML: `<a:bodyPr vert="horz" lIns="457200" tIns="45720" rIns="91440" bIns="45720" rtlCol="0" anchor="ctr"/>` — identical to steps 1, 2, and 4's `bodyPr`, which all wrap identically to the reference.
- Why the candidate is wrong: box size and insets are identical to the other three step boxes (which match the reference), so this text alone breaking differently points to a text-width/measurement discrepancy for this specific string (e.g. the curly apostrophe in "organization's") rather than a box-geometry issue. Confidence is medium since the exact cause (glyph metrics vs. wrap algorithm) isn't visible from the XML alone.
