## Reference vs candidate

This slide is a three-panel "we can help" summary: a two-line gray title, then three equal-width colored callout boxes (blue, dark blue, gray), each with a bold white heading, a white circle holding a vector icon, and a caption line below. The reference renders the title fully above the boxes, white bold headings readable on every box, and three distinct icons (magnifying glass, network/org-chart glyph, head-with-gears). The candidate shows the same layout and colors but the title's second line drops down into the top edge of the boxes, all three headings render in the same dim gray as the box fills (worst on the gray box, where the text nearly disappears), and all three icons are replaced by flat rectangles/blocky nested squares in the fill colors that should belong to the icon strokes.

## Findings

### 1. Custom-geometry icon shapes render as bounding-box rectangles

- Where: `Freeform 38` (id 39, magnifying-glass icon in the "SaaS Visibility" circle), `Freeform 43` (id 44, network icon in "Extended Granular Control"), and the nested freeform group under `Group 48` (ids 50, 52, 53, 54, 55, 56 — the head/gears icon in "Intelligent Protection"). Region roughly `[0.207, 0.454, 0.952, 0.675]` (the row of three icon circles).
- Reference: draws each icon as its actual silhouette — a magnifying glass, a cloud-over-org-chart glyph, and a head profile with gear cutouts — in the shape's `tx2`/dark-blue fill color, sitting inside the white circle.
- Candidate: draws a single flat rectangle spanning each freeform's bounding box instead of the polygon. For the nested gear icon (a group of several freeforms), each child's own bounding-box rectangle is drawn, producing a stack of overlapping light/dark squares rather than a coherent icon.
- XML:
  ```
  <!-- Freeform 38, magnifying glass -->
  <a:custGeom>
    <a:avLst/>
    <a:gdLst>...</a:gdLst>
    <a:pathLst>
      <a:path w="1484" h="1500">
        <a:moveTo><a:pt x="1442" y="1256"/></a:moveTo>
        <a:lnTo><a:pt x="980" y="794"/></a:lnTo>
        <a:lnTo><a:pt x="940" y="836"/></a:lnTo>
        ... (dozens more literal lnTo points, no arcs, no gd-formula references)
      </a:path>
    </a:pathLst>
  </a:custGeom>
  <a:solidFill><a:schemeClr val="tx2"/></a:solidFill>
  ```
- Why the candidate is wrong: the path is a plain closed polygon defined with literal coordinates against its own `w`/`h` path space — nothing here depends on the (unused) `gdLst` guides. The fill color the candidate uses on each rectangle (`tx2`, matching the correct icon color) shows color resolution is fine and the bug is isolated to `custGeom` path rasterization: the renderer appears to fall back to the shape's bounding box instead of building the outline from `a:pathLst`. This is the single largest contributor to the diff and the most severe finding — it hits every icon on the slide.

### 2. Heading text ignores the shape style's font color and renders in the default gray

- Where: the bold caption text in all three callout boxes — "SaaS Visibility" (id 36, blue box), "Extended Granular Control" (id 41, dark-blue box), "Intelligent Protection" (id 46, gray box). Region `[0.045, 0.234, 0.961, 0.454]`.
- Reference: all three headings render in solid white, bold, clearly legible against every box color.
- Candidate: all three headings render in `rgb(103,103,103)` (hex `676767`) — the theme's generic default body/title text color — instead of white. On the blue boxes this is a muddy low-contrast gray-on-blue; on the gray box (`id 46`, fill `accent3`, also `676767`) the text color exactly matches the fill and is effectively invisible (pixel-sampled: both text glyphs and background measured `(103,103,103)`).
- XML:
  ```
  <p:sp><!-- id 46, "Intelligent Protection" -->
    <p:spPr><a:solidFill><a:schemeClr val="accent3"/></a:solidFill> ... </p:spPr>
    <p:style>
      <a:fillRef idx="1"><a:schemeClr val="accent1"/></a:fillRef>
      <a:fontRef idx="minor"><a:schemeClr val="lt1"/></a:fontRef>
    </p:style>
    <p:txBody>
      <a:p><a:r><a:rPr lang="en-US" sz="2200" b="1" dirty="0"/><a:t>Intelligent Protection</a:t></a:r></a:p>
    </p:txBody>
  </p:sp>
  ```
- Why the candidate is wrong: the run carries no `solidFill` of its own, so its color must resolve through the shape's `p:style/a:fontRef` (`schemeClr lt1`, theme white) per the OOXML style-matrix rules — exactly what the reference does. The candidate instead appears to fall back to the master's generic default text color (`676767`, the same value used for the title and body placeholders), meaning shape-style font-color inheritance is not implemented or not reached for non-placeholder autoshapes with `p:style`.

### 3. Title's second line overflows its placeholder box due to wrong line spacing

- Where: `Title 1` (id 2), text "We can help. Cisco Cloud Access Security with Elastica delivers", box inherited from the master at `[0.034, 0.066, 0.926, 0.209]` (EMU `off (310855,341313)`, `ext (8469608,731837)` against a `9144000x5143500` slide).
- Reference: both lines sit inside the ~77px-tall title box (line 1 spans render rows ~35–74, line 2 spans ~76–106), fully clear of the callout boxes that start at row ~126.
- Candidate: line 1 starts ~13px lower (row ~48) and line 2 (row ~98 onward) is spaced roughly 50px from line 1's top instead of ~41px, running past row 126 and under the callout boxes, which are drawn later in z-order and paint over/through the descenders of line 2 ("with Elastica delivers" is only partially visible, cut by the box tops).
- XML:
  ```
  <!-- master.xml, titleStyle/lvl1pPr -->
  <a:lnSpc><a:spcPct val="80000"/></a:lnSpc>
  <a:defRPr sz="3200" ...><a:solidFill><a:srgbClr val="676767"/></a:solidFill></a:defRPr>
  ```
  ```
  <!-- slide6.xml, Title 1 -- no bodyPr/lstStyle overrides -->
  <p:sp><p:nvPr><p:ph type="title"/></p:nvPr>
  <p:spPr/><p:txBody><a:bodyPr/><a:lstStyle/>
    <a:p><a:r><a:rPr lang="en-US" dirty="0"/><a:t>We can help. Cisco Cloud Access Security with Elastica delivers</a:t></a:r></a:p>
  </p:txBody></p:sp>
  ```
- Why the candidate is wrong: the master's `titleStyle` sets 80% line spacing for exactly this two-line case, and the box height (731837 EMU ≈ 77px) only accommodates two 32pt lines at 80% spacing, not full single spacing. Nothing in the slide, layout, or master overrides this for the title placeholder, so the candidate's wider line gap indicates the inherited `lnSpc` is not being applied, causing an overflow that a correctly-spaced render would not have.
